# Техническое задание (ТЗ): Перевод контроля SLA заявок на реактивную модель (Time Wheel)

## 1. Цель
Заменить существующий механизм периодического опроса БД (Polling) в `RequestSchedulingService` на реактивную событийную модель с использованием структуры данных `HashedWheelTimer` (Колесо времени). Это позволит снять нагрузку с базы данных при увеличении количества активных заявок и сделать отслеживание SLA моментальным и высокоточным.

## 2. Проблематика текущего решения
В данный момент `RequestSchedulingService` раз в 15 секунд выполняет `SELECT` запросы к БД, чтобы найти все заявки со статусом `CREATED` старше 3 минут и `WAITING` старше 5 минут.
* При масштабировании системы и увеличении таблицы `requests` до миллионов строк эти частые запросы будут создавать необоснованную нагрузку на СУБД (PostgreSQL).
* Увеличивается задержка (latency) срабатывания SLA за счет интервала между запусками планировщика.

## 3. Архитектура нового решения (HashedWheelTimer + Kafka)

### 3.1. Основной принцип
1. При создании или смене статуса заявки система публикует Kafka-событие в топик `request-events` (уже реализовано).
2. Новый служебный слой (SLA Service) выступает консьюмером этого топика.
3. При получении события `CREATED` (или `WAITING`), SLA Service планирует задачу (Task) в `HashedWheelTimer` в оперативной памяти с задержкой, равной оставшемуся времени SLA (например, 3 минуты).
4. Когда таймер срабатывает, задача инициирует проверку текущего статуса заявки по первичному ключу (ID) в БД. Если статус не изменился, отрабатывает логика эскалации через `RequestSlaProcessor`.

### 3.2. Компоненты для доработки/создания

#### 3.2.1. Интеграция библиотеки Netty
Для реализации Time Wheel необходимо использовать проверенную структуру `HashedWheelTimer`.
* **Задача:** Убедиться в наличии зависимости `io.netty:netty-common` в `app/pom.xml`, конфигурация бина `HashedWheelTimer` в конфигурационном классе Spring. Конфигурация колеса: интервал тика (tick duration) — 1 секунда, размер колеса (ticks per wheel) — 512 или 1024.

#### 3.2.2. Создание `RequestSlaTimerService`
* **Роль:** Компонент, управляющий добавлением задач в таймер.
* **Функционал:**
    * Метод `scheduleWaitingCheck(UUID requestId, OffsetDateTime createdAt)`: добавляет задачу в таймер на `createdAt + 3 мин`.
    * Метод `scheduleEscalationCheck(UUID requestId, OffsetDateTime waitingAt)`: добавляет задачу в таймер на `waitingAt + 2 мин`.
    * Логика Task: при срабатывании вызывает методы из `RequestSlaProcessor` для перевода статуса в `WAITING` или `ESCALATED`. Внутри `Processor` остается перехват `OptimisticLockingFailureException`.

#### 3.2.3. Создание Kafka Consumer (`SlaEventListener`)
* **Роль:** Подписчик на топик `request-events`.
* **Функционал:**
    * Слушает топик. При получении `RequestEvent` с типом `CREATED` — вызывает `scheduleWaitingCheck`.
    * При получении `RequestEvent` с типом `WAITING` — вызывает `scheduleEscalationCheck`.
    * (Опционально) При фильтрации статусов `ASSIGNED`, `COMPLETED`, `CANCELED` — может досрочно отменять (Cancel) запланированные `Timeout` объекты в `HashedWheelTimer` для экономии памяти (потребуется `ConcurrentHashMap<UUID, Timeout>` для хранения ссылок).

#### 3.2.4. Реализация механизма восстановления (Recovery)
Поскольку `HashedWheelTimer` хранит состояние только в оперативной памяти (RAM), при рестарте приложения или падении пода (Pod) все запланированные таймеры пропадут.
* **Задача:** Создать компонент `SlaRecoveryRunner` (реализующий `ApplicationRunner` или метод с `@EventListener(ApplicationReadyEvent.class)`).
* **Логика работы:**
    1. При старте приложения делает один `SELECT` в БД: найти все заявки со статусами `CREATED` и `WAITING`.
    2. Для каждой найденной заявки высчитывает оставшееся время до SLA:
       * Для `CREATED`: Остаток = 3 мин - (Сейчас - `createdAt`).
       * Для `WAITING`: Остаток = 2 мин - (Сейчас - время перехода в WAITING, можно приблизительно использовать `createdAt + 3 мин`).  *(Примечание: в Entity `Request` нет поля `waitingAt`, возможно, потребуется его добавить для точности)*.
    3. Если остаток времени `> 0`, планирует задачу в `RequestSlaTimerService` на вычисленный остаток.
    4. Если остаток времени `<= 0` (SLA уже просрочен во время простоя сервера), немедленно вызывает методы `RequestSlaProcessor` для изменения статуса в отдельном потоке.

#### 3.2.5. Удаление старого планировщика
* **Задача:** После успешного внедрения и тестирования новой реактивной схемы необходимо пометить `RequestSchedulingService` как `@Deprecated`, отключить аннотацию `@Scheduled` или полностью удалить класс.

## 4. Этапы реализации (Roadmap)
1. **Подготовка моделей:**
   * Рассмотреть необходимость добавления поля `waitingAt` в `Request.java` и соответствующей миграции (Flyway) для точного восстановления таймера `WAITING -> ESCALATED` после рестарта.
2. **Настройка Time Wheel:**
   * Подключение зависимостей Netty.
   * Настройка Bean конфигурации `HashedWheelTimer`.
3. **Реализация сервисов:**
   * Написание `RequestSlaTimerService`.
   * Написание `SlaEventListener`.
4. **Механизм восстановления:**
   * Реализация `SlaRecoveryRunner`.
5. **Тестирование:**
   * Написание Unit и Integration тестов, имитирующих остановку приложения и проверку корректности восстановления таймеров по времени.
   * Изменение существующих интеграционных тестов `RequestLifecycleIntegrationTest` (если в них использовался `@Scheduled`).
6. **Очистка кода:**
   * Удаление старого механизма Polling.
